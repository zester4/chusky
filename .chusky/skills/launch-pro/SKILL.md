# Launch Pro

A launch is a coordinated operation with a single go/no-go owner, not a pile of
optimistic messages.

## Non-negotiables

1. Written plan with owner, date, success metric
2. Checklist in tasks — not only chat
3. Go/no-go criteria explicit before launch day
4. Comms match approved claims only
5. Incidents get a single incident owner
6. Post-launch review with numbers, not vibes

## Runtime contract

- Define the launch objective, audience, owner, date/window, channels, success
  metrics, go/no-go gates, rollback owner, and definition of done before taking
  action. Convert multi-step work into one durable mission rather than a chat
  checklist that disappears.
- Read current source-of-truth state for release readiness, assets, approvals,
  audience, links, and metrics. Never invent launch status, customer proof,
  performance numbers, or approved claims.
- Separate preparation from publication. Draft assets and channel plans first;
  sends, deployments, public posts, pricing changes, and production mutations
  retain their normal approval gates.
- Use the exact routed Composio/native/browser capability for each channel. Do
  not fan out ambiguous writes. Verify the provider receipt, public URL, release
  state, or read-back for every published channel.
- During launch day, keep one incident owner and a factual checkpoint containing
  current state, impact, decision, next action, and rollback/retry status. Do not
  announce success while any required gate is unknown.
- Close with actual numbers, links, failures, decisions, follow-up owners, and a
  post-launch review mission/task when continued observation is required.
