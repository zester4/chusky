---
title: SDK releases
description: Validate, version, publish, and track Chusky SDK releases.
---

The canonical SDK source is the separate [`zester4/chusky-sdk`](https://github.com/zester4/chusky-sdk) repository. Its **Release Chusky SDK** workflow automatically validates and publishes when `package.json` or `package-lock.json` changes on `main`. It also supports a manually dispatched exact version and `sdk-vX.Y.Z` tags for recovery. The agent monorepo's release workflow is a guarded fallback; never start two releases for the same version concurrently.

The checked-in SDK mirror currently contains `1.15.1`. The latest published
package is `1.15.0`; publish and tag `1.15.1` only after the canonical
repository's release checks pass.

## 1.15.1 — Mission execution fences

- Expose mission-step `allowedTools` as a typed execution fence, including an
  explicit empty list.
- Keep provider-read verification out of explicitly tool-less worker slices and
  prevent model-driven replans from widening their current tool fence.
- Honor creation-time budget ceilings and recover retryable scheduling failures
  when a mission is retried with its original idempotency key.

## 1.15.0 — Run progress

- Add typed `RunProgress` data to run snapshots and append-only `run.progress`
  stream/replay events for planning, research, action, approval, and completion.
- Keep progress and evidence bounded and provider-neutral; raw tool arguments,
  connected-app payloads, credentials, and results are never included.

## 1.14.0 — Private meeting mission state

- Expose bounded owner-private meeting mission state in typed meeting records,
  including decisions, open questions, commitments, next move, and checkpoint.
- Shared meeting projections continue to omit this private working state.

## 1.13.0 — Verified trigger action context

Dashboard actions for connected-app trigger events can now continue in Chat with
the saved event and selected action attached to the run request.

- The API verifies the trigger event belongs to the authenticated owner before
  admitting the run.
- When the event has persisted suggested actions, the selected action must be
  one of those actions; missing, foreign, or unknown actions are rejected.
- Event summaries and provider-derived results remain context, not
  authorization. Consequential work still uses the normal approval and
  provider-safety boundaries.

## 1.10.0 — Attention Pulse

The TypeScript SDK now exposes `chusky.attentionPulse.get()` and
`chusky.attentionPulse.update()` for Elena's proactive operating loop.

- Configure cadence, authority, monitored domains, quiet hours, daily delivery
  limits, and explicitly opted-in Telegram or dashboard delivery.
- Use idempotency keys for safe retries of preference updates; the API validates
  the authenticated owner before changing the pulse.
- Treat pulse messages as accountable observations and proposed next actions,
  not as proof that an external provider write happened.
- Reversible preparation can run within the configured authority. Consequential
  actions remain behind the normal approval boundary.

For the normal release:

1. Update the SDK source, changelog, and package version in the dedicated SDK repository. Keep `package.json` and `package-lock.json` versions in sync.
2. Run `npm ci`, `npm run typecheck`, `npm run build`, and `npm test` in that repository.
3. Commit and push the changes to `main`. GitHub Actions reruns those checks, publishes `@chusky/sdk`, and creates the matching `sdk-vX.Y.Z` tag and GitHub release.
4. Confirm the exact npm version, tag, and successful workflow run before announcing the release.

The SDK repository must have an `NPM_TOKEN` Actions secret with publish access to `@chusky/sdk`; `GITHUB_TOKEN` is used for tags and GitHub releases. The package is public. Provenance is intentionally omitted because npm's provenance repository validation does not accept this private source repository's identity. A repeated automatic push for an already published version is a no-op; manual duplicate releases fail clearly.

From the agent monorepo, `npm run sdk:check` validates its SDK mirror. To preflight an exact version without publishing, run:

```bash
npm run sdk:publish -- --version 1.15.1 --dry-run
```

The preflight verifies that the manifest and lockfile agree and runs the SDK's publish lifecycle checks. Prefer publishing from the dedicated SDK repository; do not change the package repository URL to the agent monorepo.
